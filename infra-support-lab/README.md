# Infra Support Lab

Небольшой учебный инструмент для технической поддержки Windows/Linux: проверяет доступность сервисов, свободное место и резервную копию обычных файлов. Формирует JSON для автоматизации и HTML для разбора инцидента. Python 3.10+, без pip-зависимостей.

## Быстрый запуск

Откройте терминал **в корне репозитория**. В Ubuntu используйте `python3` вместо `python`, если команда `python` отсутствует.

```console
python -m infra_support demo
python -m unittest discover -s tests -v
```

Демо поднимает временный TCP-сервис на `127.0.0.1`, создаёт файл и ZIP, выполняет четыре проверки, затем делает копию просроченной на 48 часов и повторяет проверки. Внешняя сеть, Docker, административные права и SQL Server не нужны. Временные данные удаляются после выполнения.

Откройте `reports/demo/healthy.html` и `reports/demo/incident.html`. Соседние JSON содержат те же результаты и длительность проверок. Ожидаемый вывод:

```text
Healthy: OK; stale-backup incident: FAIL
```

Это демонстрация обнаружения просроченного бэкапа, а не работающий стенд Active Directory/Exchange/SQL Server. Время выполнения и адрес временного TCP-порта меняются при каждом запуске.

## Проверки своего стенда

```console
python -m infra_support check --config configs/local.example.json --output reports/local
```

`configs/infrastructure.example.json` показывает настройки SMB (445), LDAP (389), SMTP (25), SQL и бэкапа. Скопируйте его в `configs/infrastructure.local.json` и укажите адреса своих сервисов. Пример использует loopback: без соответствующих сервисов проверки будут FAIL, это ожидаемо. Относительные пути разрешаются **от папки конфигурационного файла**. Неизвестные поля и неверные пороги отклоняются до проверок.

| Тип | Что проверяет | Обязательные поля кроме name/type |
| --- | --- | --- |
| `dns` | Разрешение имени системным DNS-резолвером | `host` |
| `tcp` | Возможность установить TCP-соединение | `host`, `port` |
| `disk` | Долю свободного места на томе | `path`, `min_free_percent` |
| `backup` | Возраст ZIP по mtime, наличие файлов и CRC | `path`, `max_age_hours` |
| `mssql` | Реальный запрос `SELECT 1` через установленный sqlcmd | `server` |

`tcp` принимает `timeout` в секундах, по умолчанию 3; `mssql` — по умолчанию 5. Максимум 30 секунд. Для sqlcmd отдельно ограничены подключение, запрос и время процесса. У DNS таймаут задаёт системный резолвер; TCP timeout также не ограничивает предшествующее разрешение имени. Если нужен предсказуемый TCP timeout, указывайте IP. Проверки последовательные, без фоновой службы и без уведомлений.

Коды завершения команды `check`: `0` — всё OK, `1` — минимум один FAIL, `2` — ошибка конфигурации, аргументов или записи отчёта. `demo` возвращает `0`, если оба ожидаемых сценария воспроизведены. Отчёты с тем же именем перезаписываются; при планировании выбирайте отдельный каталог для каждого запуска или архивируйте их.

## Резервное копирование

```console
python -m infra_support backup --source ./sample-data --destination ./backups/files.zip
```

Сначала создайте `sample-data` и положите туда тестовые файлы. Каталог назначения должен быть вне источника. Уже существующий архив не перезаписывается. Используйте новое имя при повторном запуске. Символические ссылки и обнаруженные junction-каталоги не поддерживаются. Пустой источник отклоняется.

Архив проверяется методом ZIP CRC. В тестах файлы также восстанавливаются во временный каталог и сравниваются побайтно. Для ручной проверки распакуйте созданный архив в новый пустой каталог и сравните с источником. Инструмент предназначен для небольшого доверенного набора обычных файлов: нет VSS, сохранения ACL, согласованного снимка изменяемых файлов, ротации или шифрования. Для работающей СУБД используйте её штатные средства BACKUP/RESTORE, а не копирование файлов базы.

## Microsoft SQL Server

Установите Microsoft `sqlcmd` отдельно и настройте доступ к своему серверу. По умолчанию используется `-E`, то есть integrated authentication. В Linux для этого необходима соответствующая настройка Kerberos. Выполняется только `SET NOCOUNT ON; SELECT 1;`: создание или изменение данных не требуется.

При SQL-аутентификации добавьте `"username": "reader"` к проверке и задайте пароль через `SQLCMDPASSWORD` в текущем окружении. Пароль не сохраняется в конфигурации, не передаётся аргументом `-P` и не пишется в отчёт. Не используйте административную учётную запись. Проверка сертификата не отключается; для локального SQL Server настройте доверенный сертификат. Исходный вывод sqlcmd не включается в отчёт, поэтому подробности ошибок подключения проверяйте отдельно в своей среде.

Обработка sqlcmd покрыта тестами с подменённым процессом. Это не проверка подключения к настоящему SQL Server; такой запуск требует отдельного стенда.

## Bash и PowerShell

Диагностические скрипты только читают состояние машины и выводят его в терминал:

```bash
bash scripts/diagnose-linux.sh
```

```powershell
.\scripts\Diagnose-Windows.ps1
```

Linux: сведения об ОС, дисках, IP-адресах, маршрутах, резолвере, сбойных systemd-сервисах и слушающих TCP-сокетах. Windows: ОС, диски, IP/DNS, состояние установленных инфраструктурных служб и слушающие TCP-сокеты. Служба `Dhcp` в Windows — DHCP-клиент. Отсутствие компонента на машине не означает сбой удалённого сервиса.

Скрипт Windows рассчитан на Windows PowerShell 5.1 / PowerShell 7 под Windows. Если локальная политика блокирует запуск, используйте разрешённый в вашей среде способ запуска; менять системную политику для проекта не требуется. Вывод содержит сведения о машине и сети: храните диагностические выгрузки локально. `reports/`, `backups/`, `.env`, `*.local.json` и диагностические файлы исключены из Git.

## Ограничения проверок

- TCP-порт SMB/LDAP/SMTP может открываться даже при неисправном приложении. Здесь нет проверки доступа к общей папке, LDAP bind и доставки письма.
- `dns` проверяет ответ системного резолвера, который может прийти из hosts или кеша; конкретный DNS-сервер не опрашивается напрямую.
- DHCP не проверяется: ему нужны UDP и проверка выдачи аренды в изолированном стенде. Нет развёртывания AD, Exchange, Zabbix или Nagios.
- Свежесть ZIP определяется mtime; успешный CRC не заменяет полноценную проверку восстановления и не подтверждает отсутствие подмены.
- Нет постоянного мониторинга или промышленного SLA. Отчёт — снимок состояния на момент запуска.

## Структура

```text
infra_support/cli.py           проверки, отчёты, ZIP и демо
configs/                      примеры конфигурации
scripts/                      диагностика Bash и PowerShell
tests/                        unittest, локальные TCP/ZIP сценарии
docs/incident-runbook.md       порядок разбора инцидентов
.github/workflows/ci.yml       тестовая матрица Windows/Ubuntu
```

GitHub Actions настроен на Python 3.10 и 3.12 под Windows и Ubuntu. Факт успешного облачного прогона появится только после загрузки репозитория и выполнения workflow.

Результаты выполненных локальных проверок и их границы: [docs/validation.md](docs/validation.md).

## Публикация на GitHub

Создайте пустой репозиторий `infra-support-lab` в своём аккаунте без автоматически добавленного README. Выполните в корне **этого проекта**, а не на рабочем столе:

```console
git init
git add .
git diff --cached --stat
git commit -m "Add infrastructure support lab"
git branch -M main
git remote add origin https://github.com/talvikettu/infra-support-lab.git
git push -u origin main
```

Перед коммитом просмотрите подготовленные файлы: локальные конфиги и отчёты не должны попасть в репозиторий. Ссылка выше — планируемый адрес нового репозитория, не подтверждение публикации. Резюме хранится отдельно от проекта.
